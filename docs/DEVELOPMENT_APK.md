# Development APK: local MCP and authenticated ngrok diagnostics

The signed Android workflow now emits **release** and **development** APKs from one source commit. Development uses the same `dev.pocket.agent` application ID and **distribution signing key** as release, so it can be installed over release and access the same app-private SQLite history. Development includes its own notification-backed diagnostics server and Settings entry; release does **not** include this debugging server or activity. Both variants include the separate production ChatGPT MCP connector and its ARM64 ngrok tunnel. Installing release over development removes the debugging bridge code; stop the debugging bridge first.

## Downloads and schedule

Bookmark the [**Development prerelease**](https://github.com/ru-aish/pocket-agent/releases/tag/development). Under **Assets**, download:

- **`Pocket-Agent-development-arm64.apk`** for an ARM64 phone ([direct download](https://github.com/ru-aish/pocket-agent/releases/download/development/Pocket-Agent-development-arm64.apk)).
- **`Pocket-Agent-development-x86_64.apk`** for an x86_64 emulator.
- **`Pocket-Agent-development-universal.apk`** if unsure which architecture to use.

The **Scheduled development APK** workflow runs at **00:17, 03:17, 06:17, 09:17, 12:17, 15:17, 18:17 and 21:17 UTC** (`17 */3 * * *`). It pins the current `main` commit and compares it with the source recorded in the last complete, published development release. If unchanged, the APK build job is skipped. A missing/incomplete release is rebuilt; a failed build or publication does not record a successful source, so the next run retries. The first successful run creates the prerelease; later runs replace its assets and move only the `development` tag to the built commit. Stable releases keep their existing tags and Latest status.

The schedule becomes active once `.github/workflows/development-apk.yml` is merged into `main` (the default branch). GitHub may delay scheduled runs. To check status or trigger an earlier check, open [**Actions → Scheduled development APK**](https://github.com/ru-aish/pocket-agent/actions/workflows/development-apk.yml), choose **Run workflow** on **main**, and open the run. Manual runs use the same unchanged-source check. A successful build also has a **`pocket-agent-development`** artifact at the bottom of its run page, retained for 30 days; extract that ZIP to get the APKs. Release assets remain available at the bookmark above until replaced.

No new secrets are required: this workflow uses the existing `APK_KEYSTORE_BASE64`, `APK_STORE_PASSWORD` and `APK_KEY_PASSWORD` repository secrets and the workflow's `GITHUB_TOKEN` with `contents: write` for publication. It runs the runtime tests, builds and lints the development variant, and verifies APK signatures and ARM64 ngrok packaging. These scheduled snapshots do not run the full emulator suite; the existing **Signed Android APK** workflow continues its validation on pushes.

## Recorded data

`agent-state.db` already stores the durable Pi runtime checkpoint (`runtime_state`) including `mainMessages`, `workerMessages`, tool transcripts, and the pending completion inbox. The independent `snapshot` row contains UI state. The events table logs startup/errors and, in development, bounded tool-start/end activity (the newest 2,000 entries). Native mutation receipts are separately persisted by `OperationStore`; `phone_operation` queries them. Memory is another private database. **Logs are not full Android logcat, raw Shizuku logs, screenshots from past sessions, or provider transport traces**; images are intentionally omitted from checkpoints. Events and stored transcript are locally retained until DB deletion/uninstall, explicit worker removal, or capacity policies; event diagnostics are a rolling window.

## Start it

1. Install the CI-signed `Pocket-Agent-development-arm64.apk` (or x86_64 for emulator). The CI signs release and development with the same key and verifies both packages.
2. In Pocket Agent, open **Settings → Development MCP and ngrok**. A visible foreground-service notification remains while enabled.
3. Tap **Start USB / localhost server** to bind `127.0.0.1:8767` on the phone.
4. On Fedora, run `adb -s <device-serial> forward tcp:8767 tcp:8767` (omit `-s <device-serial>` if only one device is connected). The PC MCP endpoint is `http://127.0.0.1:8767/mcp`.
5. USB/localhost MCP requests require no Authorization header. This is intentional for local debugging; any process that can reach the forwarded host port can control the phone, so keep the ADB forward local and stop the bridge when finished.
6. For wireless access, first save the **ngrok authtoken** in that page (encrypted by Android Keystore), **stop the local bridge**, then select **Start wireless ngrok bridge**. On ARM64 devices the app loads a development-only ngrok native library from Maven Central, creates an ngrok HTTPS tunnel to its loopback port, and shows the resulting `https://…/mcp` URL. Tap **Copy wireless MCP bearer token** and authenticate wireless requests with `Authorization: Bearer <token>`. The MCP bearer is different from the ngrok authtoken and must never be committed or logged. Cellular/wifi must be functioning; ngrok plan limits and Android background execution still apply.
7. Use `tools/list` for the exact main model tool schema and diagnostic tools. Read-only `debug_history` supports optional `query`, `conversationId`, `limit`, `offset`. `debug_events` supports query/limit/offset, and `debug_state` returns the last rendered state. Other tools run through the existing main-runtime tool implementations with a dedicated `dev-mcp` screen lease. Direct phone mutations require their usual operation IDs and receipts.
8. **Stop development bridge** when done. To use the release APK, install the release variant with the same signing certificate. If you uninstall instead of replacing, Android deletes the app's private history.

## Security and testing

The bridge is **off by default** and binds only the phone loopback. USB/localhost mode intentionally has no MCP bearer; access control is the local-device/ADB boundary, so any process that can reach the forwarded port has privileged phone access. Wireless/ngrok mode requires a random 256-bit MCP bearer for every request. Both modes reject HTTP browser Origins, limit JSON bodies to 1 MiB, bound concurrent work, reject unsupported `MCP-Protocol-Version` headers, and fall back to `2025-11-25` when an `initialize` request proposes an unsupported version. If the Android runtime is not ready, `tools/list` returns HTTP 503 rather than advertising a partial list. HTTPS/ngrok provides transport encryption; the wireless MCP bearer controls privileged remote access. Do not publish the wireless URL/token in an issue, PR, CI log or screenshot. Rotate a compromised wireless bearer using **Rotate wireless MCP bearer** after stopping the bridge; this preserves chats and invalidates the old token for subsequent wireless bridge starts. Replacing the APK does not automatically rotate it.

Validation: `cd runtime && npm ci && npm test && npm run build`; `./gradlew -PdevEmulatorTest :app:assembleDevelopmentAndroidTest`; run `DevBridgeDeviceTest` against the development APK on the same emulator. Verify local requests succeed with no bearer, bearer-enabled mode returns 401 for missing/wrong credentials, browser Origins return 403, main-model tool names appear in `tools/list`, history search works, process-restart persistence works, release APKs contain no dev classes/ngrok, and local `adb forward` works. Wireless ngrok requires an ARM64 device; the x86_64 emulator build supports local MCP only. A real ngrok token and device connectivity are needed to verify wireless end-to-end; do not claim that path succeeded based only on compilation.

Production and development builds must be separately tested for Android operation safety. The development bridge is not an invisible service and intentionally does not auto-start at boot.
